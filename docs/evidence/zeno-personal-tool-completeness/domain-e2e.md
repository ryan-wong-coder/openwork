# Synthetic personal-domain integration

The final local CLI run passed all 3 tests and 114 assertions. The source is `apps/server/test/zeno-personal-domain-e2e.test.ts`; the exact successful output is in `domain-e2e.cli.txt` and a sanitized machine-readable summary is in `domain-e2e.result.json`.

The fixture uses the registered V1 native tool, the real private discovery and loopback `/personal` bridge, both native personal services, the real PKCE authorization/approval/token flow, and `createApp` with a disposable SQLite database. Accounts are randomly named reserved `example.test` identities with private random passwords. Neither record/auth/sync logic nor HTTP is mocked.

The checks cover Chinese catalogue search for canonical exercise `0025`, writing a routine from its returned ID, real API and tool readback, and versioned undo tombstones. A calendar event traverses the same write/read/undo chain. Real batch API mutations create 501 synthetic memberships; three read pages return all 501 unique records while each traverses two actual API sync pages. A second real invited account verifies custom-exercise and record isolation. Invalid, foreign, and noncanonical exercise IDs are rejected. Feature-off writes fail, scheduled or unknown sessions cannot write routines, and scheduled proposals remain pending without changing a routine. Closed-window and disconnected-account results are verified, including no fabricated records.

Credential encryption uses an explicitly named ephemeral AES-256-GCM fixture adapter. This does not test OS Keychain or Electron safeStorage. No desktop window, real account, model request, deployment, packaged binary, or full OpenCode model session is involved. Cleanup deletes the temporary database, native profiles, device credentials, and discovery file, and asserts that the private fixture directory is gone. Evidence includes no passwords, tokens, cookies, raw database contents, private temporary paths, or external identities.
