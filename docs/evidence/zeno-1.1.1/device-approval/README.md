# Device approval and the record writer lock

The original production PWA was reproduced with a real isolated API and two authenticated tabs of one synthetic account. Tab A held the actual Web Locks record writer lease. Tab B opened a newly generated device authorization link: its code was prefilled, but the input and approval button were disabled. The device's real PKCE poll remained pending. [Before](local-before/report.json) uses the frozen `29ed8c40…` PWA; its successful harness verdict means the reported bug was reproduced.

The product change removes the record-writer dependency from the approval input, button and submit guard. The independent account feature gate and bound-account server request remain. Calendar, fitness, tasks, preferences, drafts and outbox writes retain their single-writer checks. Device revocation, password changes and administrator account actions were already independent of the record lock.

The rebuilt production PWA passed [ten actual two-tab checks](local-after/report.json): UI approval, PKCE exchange, device/account binding and the real server device list; single-use grant rejection; invalid-code rejection; denial of approval through a device bearer; feature-off UI and forged-submit rejection; independent server feature denial; unchanged personal records and writer ownership. No model was called. The [success screenshot](local-after/second-tab-approved.png) was actually viewed and its size/SHA-256 independently verified. It shows the read-only record banner and disabled preferences alongside a successful server-only approval; the authorization input is empty.

Real React regressions failed twice before the fix and passed afterward (5 tests, 30 assertions). App TypeScript checking and `build:personal` passed. The frozen rebuilt index SHA-256 is `33a3b317539c456f01a7bbf63608cc2dffa8e5a5f5b855cf9b6c7917d71f3e0e`. [Validation](validation.json) records the build and test scope.

The retained [first harness attempt](local-before/attempt-1-harness-status.json) stopped before opening the second tab because the new driver initially expected HTTP 200 rather than the API's existing 201 for authorization creation. Its initial two-tab scope field describes intent, not a completed observation. The exact 201 expectation was corrected before the successful old-PWA reproduction; no API or security gate was changed.

The local checks are loopback, isolated synthetic-account checks, not an installed-desktop result. API/database/schema and frozen installer tag were not changed. The temporary local API, Chrome, database and profiles were removed. The separate [public owned-account HTTPS acceptance](public-after/README.md) passed after the PWA hotfix deployment; its registration, manual approval, PKCE binding and cleanup boundaries are recorded independently.
